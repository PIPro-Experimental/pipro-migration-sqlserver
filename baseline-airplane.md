# Baseline: the airplane rehearsal

The reference figures from the last full conversion of the airplane test client,
run 2026-10-02. That dataset is being retired in favour of a real client's live
data, so these numbers cannot be reproduced afterwards — they are recorded here
to judge whether a new client's results are plausible.

Treat them as a *shape*, not a target. A different client has different employee
counts, a different code catalogue and different promoted ordinals. What should
carry over is the **relationships** between the numbers, listed at the bottom.

## The client

| | |
|---|---|
| Legacy SQL Server database | `pipro` (DatabaseCatalog description "airplane") |
| Payrolls | 1, legacy payroll number 1 |
| Employees | 187 |
| Tenant | `tenant_test_airplane`, payroll id 1 |
| Tax year in the live DB | 2026 (March–June ran; June was the last live run) |

Caveat on this dataset: it is a real client's payroll sanitised for testing, and
three separate sanitising steps each destroyed an identity signal — 17 employees
have hashed surnames, every ID number was regenerated by the interim `id8001`
job, and two IDs therefore collide. **No identity-based check can be validated
against it.** Value-level checks are unaffected and are what these figures cover.

## Key map

187 matched, 0 `interim_only`, 0 `pipro_only`, `legacy_empno` resolved 187/187.
No duplicate codes, no zero codes, no orphan child rows, no orphan minted users.

The surrogate-coincidence trap check reports **187/187 coincide** — on this
client the interim auto-key happens to equal the legacy EmpNo, which is why a
`'emp-' || <legacy EmpNo>` join appears to work here and will silently mismatch
elsewhere. Never rely on it; use the map.

## Leave history

| | Rows |
|---|---|
| `PW_LeaveHistory2` total | 8,920 |
| orphaned (EmpNo absent from `PW_IMF`) | 5,725 |
| importable (employee exists) | 3,195 |
| survives `FromDate > EngageDate` | 1,489 |

None of the 5,725 orphans fall inside a five-year retention window, so filtering
on the current employee set loses nothing retention would not drop anyway.

**Legacy row counts are not a valid import target.** A report claiming "8,920 in,
3,195 out, 64% lost" would be wrong: legacy has no referential integrity and
nothing ever swept the orphans.

Totals are 4dp because legacy `Amt` is a **float** — 16,195.62 is physically
stored as 16195.619999999999, rounded to 4 on capture.

## What should carry over to a new client

The counts will all differ. These relationships should not:

- legacy alpha rows − promoted rows = carried alpha rows, **exactly**
- amount routing total = `PW_Amts` row count, with **zero quarantine**
- `employee_code` unique across the tenant once qualified `<payroll>/<EmpNo>`
- key map: 0 `interim_only` (anything there is a silently dropped employee), 0
  orphan minted users, `legacy_empno` resolved for every row
- master-data diff: nothing under `value_differs`, `only_in_a` or `only_in_b`
- run comparison: both sides on the **same period** before any figure is read
